# ТЗ-215 — Фикс бутового раннера schema.sql для чистой установки PostgreSQL

> Дата: 2026-11-13 · Статус: открыто
> Выявлено при: чистой установке тестового контура на VPS 217.114.7.184
> Класс: баг штатного пути (как инциденты 2026-10-01 compose / 2026-10-04 Caddyfile)
> Зафиксировано в: `DEPLOYMENT.md` §«⚠️ 2026-11-13: чистая БД PostgreSQL…»

---

## 1. Контекст

Бэкенд при старте (PostgreSQL-режим) применяет базовую схему из
`src/models/schema.sql` — `src/index.ts`, шаг 1 инициализации (~строки
3942–3968):

```ts
const schema = fs.readFileSync(schemaPath, 'utf-8');
const statements = schema.split(';').filter(s => s.trim());
for (const stmt of statements) {
  await query(stmt + ';');   // WARN при ошибке, кроме "already exists"
}
```

Это единственный путь создания схемы на свежем кластере PG (на проде схема
пришла из дампа Render 2026-09-02, поэтому раннер существует в вечном no-op и
баг не проявлялся 2+ месяца).

## 2. Проблема

`schema.split(';')` **не вырезает SQL-комментарии до сплита**. В `schema.sql`
комментарии содержат точки с запятой, например:

```sql
-- получают индекс сразу; на существующих базах — миграция users_username_lower_unique_idx.
```

Split разрезает файл по этой `;` → фрагмент `на существующих базах — миграция…`
уходит в `query()` как отдельный statement → `syntax error at or near "на"`.
Каскад последствий на свежей БД:

1. Часть CREATE TABLE молча не создаётся (users, payments, portfolios,
   courses и др. — зависит от положения повреждённых фрагментов).
2. Бэкенд стартует «успешно» (ошибки логируются как WARN), порт слушается,
   `/api/health` отвечает OK — деплой выглядит здоровым.
3. Фоновые воркеры сыплют ошибками: `relation "fact_check_jobs" does not exist`,
   `relation "fact_check_requests" does not exist`, `column "locked_at" does
   not exist` (fact-check воркеры крутятся в цикле ошибок).
4. `GET /health` (детальный) показывает `"db": "error"` — сигнатурный запрос
   падает на отсутствующей таблице `courses`. Это единственный видимый
   снаружи симптом.

Симптомы при чистой установке 2026-11-13 (217.114.7.184):

```
[PostgreSQL] WARN: syntax error at end of input
[PostgreSQL] WARN: syntax error at or near "-"
[PostgreSQL] WARN: syntax error at or near "на"
[FactCheckWorker] Queue processing error: relation "fact_check_jobs" does not exist
```

## 3. Цель

Бутовый раннер корректно применяет `schema.sql` на пустом кластере PostgreSQL:
все таблицы и индексы создаются, WARN'ов синтаксиса нет, `/health` после
старта на свежей БД отдаёт `db: { news: 0, users: 0, courses: 0 }`.

## 4. Задачи

### Задача 1 — вырезание комментариев до split (ядро фикса)

В раннере схемы (`src/index.ts` ~3942–3968) добавить вырезание `--`-комментариев
**до** `split(';')` — по образцу эндпоинта `/migrate-lms` (~строки 959–968):

```ts
const cleaned = schema
  .split('\n')
  .map((l: string) => {
    const i = l.indexOf('--');
    return i >= 0 ? l.slice(0, i) : l;
  })
  .join('\n');
const statements = cleaned.split(';').filter(s => s.trim());
```

Оговорка та же, что в `/migrate-lms`: строковых литералов с `--` внутри
schema.sql нет (проверить grep'ом `'[^']*--` перед мерджем; если появятся —
нужен полноценный tokenizer, см. Задачу 3).

### Задача 2 — защита от молчаливой деградации (fail-loud)

Ошибки раннера, отличные от `already exists`, на схеме, где целевых таблиц нет,
не должны проходить незамеченными:

- после применения схемы проверить существование канареечных таблиц
  (`users`, `news`, `subscription_plans`) через `to_regclass`;
- если хоть одной нет — логировать ERROR-уровнем
  `[PostgreSQL] Schema INCOMPLETE: <список>` (по аналогии с boot-логом
  `[Email] Config: …` — потеря env видна в логах сразу, не по жалобам);
- HTTP-порт при этом всё равно поднимать (контракт TZ-20 «сначала порт»),
  `/health` честно показывает `db: "error"`.

### Задача 3 (опционально, отдельным ТЗ) — общий SQL-runner

Раннеры схемы/миграций дублируются в 4+ местах (бут schema.sql, бутовые
lms/mcp/weekly/telegram_club, эндпоинты `/migrate-*`), каждый со своей
обработкой комментариев. Вынести единый `applySqlFile(path)` с корректным
парсингом (комментарии + строковые литералы + dollar-quoting), перевести все
call-site'ы на него.

### Задача 4 — регрессионный тест чистой установки

`scripts/probes/` или CI-шаг: поднять пустой PG (pgvector:pg18), запустить
бут бэкенда против него, проверить:

1. в логах бэкенда нет `syntax error` от раннера схемы;
2. `SELECT to_regclass('public.users')` и ещё ~10 канареек — не NULL;
3. `GET /health` → `db` — объект, не `"error"`;
4. регистрация пользователя + `/api/news` с токеном → 200.

После зелёного теста — убрать workaround из `DEPLOYMENT.md`
(§«⚠️ 2026-11-13» пометить «исправлено в <commit>»).

## 5. Критерии приёмки

- [ ] На свежем кластере PG бут создаёт полную схему без WARN'ов `syntax error`.
- [ ] `/health` после бута на пустой БД: `"db": {"news":0,"users":0,"courses":0}`.
- [ ] Фact-check воркеры стартуют без `relation does not exist`.
- [ ] На проде (существующая БД) — поведение без изменений: всё no-op,
      ноль миграционных побочек (это ТЗ без миграций БД).
- [ ] `DEPLOYMENT.md`: workaround-раздел помечен исправленным.

## 6. Риски

| Риск | Митигация |
|------|-----------|
| В schema.sql есть строковый литерал с `--`, который сломается линейным вырезанием | grep-проверка перед мерджем; иначе Задача 3 |
| Правка трогает бут всех сред (prod при пересоздании контейнера) | раннер и так no-op на prod; добавить канареечную проверку (Задача 2) — она только логирует |
| Дублирование логики с `/migrate-lms` разойдётся снова | Задача 3 — единый runner |
