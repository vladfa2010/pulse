# Методология поиска новостных каскадов в PULSE

> Собрано по итогам экспериментов 2026-09-05. Данные: 9 999 новостей за 7 дней
> (29.08–05.09 2026), полученных через публичный API. Документ фиксирует всю логику:
> от получения выборки до продакшен-правил.

---

## 1. Концепт

**Новостной каскад** — цепочка перепечаток одного факта разными источниками с переписанными
заголовками. Задачи:

1. Найти дубли в ленте.
2. Определить **первую новость** (первоисточник) и хронологию дублей.
3. Отобразить каскад на графике актива: первая новость — крупный маркер, дубли — мелкие.
4. Двухуровневая модель: **сюжет** (история, живущая сутками) → **каскады** (перепечатки
одного факта внутри сюжета).

**Критерий дубля (для человека и для LLM):** новость сообщает *тот же ключевой факт без
существенно новой информации*. Контрпримеры (НЕ дубли):

- одно событие, разные новости («Сбер отчитался» vs «Аналитики прокомментировали отчёт»);
- один брифинг, разные тезисы (заявления Нарышкина: риск конфликта ≠ планы ЕС к 2030);
- ежедневные сводки с разными числами (85 дронов вчера ≠ 516 сегодня);
- развитие истории (закрытие консульства → ответ МИД — разные факты).

## 2. Главные факты о данных (измерено)

1. **Дословный дедуп мёртв**: `content_hash = MD5((title_ru || title) + "_" + (summary_ru || summary), первые 500 символов)` (`src/services/rssFetcher.ts:342`; в TAGS_AND_ARTICLES.md §3.1 ошибочно указан SHA256 — сверено с кодом 05.09) сработал 5 раз из 9 999 (0,05%). У всех остальных
`source_count = 1`. Каждый источник переписывает заголовок → хэш разный → дубли живут
как отдельные записи. **Вся дупликация семантическая.**
2. **Доля перепечаток в ленте**: 448 новостей из 9 999 (4,5%) входят в подтверждаемые
эвристикой межисточниковые кластеры. Это **нижняя граница** — сильно переписанные
заголовки без общих слов эвристика не видит.
3. **Скорость каскада**: медиана первого дубля — 33 мин; 18% — в течение 10 мин;
64% — в течение часа. Хвост «догоняющих» — до 3+ часов и суток.
4. **Первоисточники** (по 171 чистому кластеру): Интерфакс 35% (first-rate 63%),
TG Parser 23% (first-rate 58%), Ведомости 12%, Коммерсант 12% (first-rate 20% —
хаб перепечаток), Известия 7% (first-rate 60%). Первенство зависит от темы —
список «wire-источников» хардкодить нельзя.
5. **Найден баг проде**: у части новостей OilPrice.com/MarketWatch в `title_ru` лежит
сырой JSON промпта переводчика (`{"prompt":"You are a senior financial news editor...`).
Каскад-детектор склеил их в кластеры с sim≈1 — работает как монитор качества данных.

## 3. Получение тестовой выборки

### Способ A. Публичный API (использован в экспериментах)

```javascript
GET https://pulse-api-bsov.onrender.com/api/news/global?page=N&limit=100
```

- Без авторизации, пагинация до 100 на страницу, окно 90 дней (`timeFilterSql`,
`src/services/newsReads.ts:16-20`).
- 100 страниц ≈ 90 секунд. Ответ содержит: id, title_ru, title_original, summary_ru,
source, url, published_at, matched_tags, source_count, all_sources.
- Фильтрация по тегу — локально по `matched_tags`.

⚠️ `GET /api/news/tags/:tagId` (`src/routes/news.ts:291`) зашит на LIMIT 50 — для
экспериментов не подходит, только `/global` + локальный фильтр.

### Способ B. Прямой SQL (для прода)

```sql
SELECT id, title_ru, summary_ru, source, published_at, matched_tags, source_count, all_sources, url
FROM news
WHERE matched_tags @> ARRAY['россия']::text[]
  AND published_at > NOW() - INTERVAL '72 hours'
ORDER BY published_at ASC;
```

Для обогащённых статей (enrichment_version=2) — через `news_tag_links`:

```sql
SELECT n.id, n.title_ru, n.summary_ru, n.source, n.published_at, l.tag_id, l.impact_score
FROM news_tag_links l JOIN news n ON n.id = l.news_id
WHERE l.tag_id = 'россия' AND n.published_at > NOW() - INTERVAL '72 hours'
ORDER BY n.published_at ASC;
```

## 4. Пайплайн v4 (итоговый, проверенный)

Эволюция: v1 словарный TF-IDF ≥0.45 (1 пара — почти ничего не ловит) →
v2 слова+символы ≥0.18 (много мусора) → v3 +окно 36ч и числа (цепочки «всё про Путина») →
v4 ниже.

### Стек эксперимента (важно для интерпретации результатов)

В сендбоксе **не использовались ни нейросетевые эмбеддинги, ни LLM**: сходство
заголовков — чистый TF-IDF из sklearn (статистика частот слов и символьных
фрагментов), плюс эвристики поверх (числовое вето, окно 36 ч, union-find).
Сюжеты собраны вручную (агент как куратор) — алгоритмической группировки
второго уровня не было.

Следствие: TF-IDF измеряет только **лексическое** пересечение. Полностью
переписанные заголовки («Банк России поднял ставку» → «ЦБ ужесточил ДКП»)
детектор не видит — это подтверждено замером на эталонных сюжетах: 122 из 154
их новостей не вошли ни в один каскад (§8, вкладка «Граф»). То есть результаты
эксперимента — **нижняя граница** качества; переход на эмбеддинги (§6) нужен
именно для закрытия этого провала recall, а не «для красоты».

### Шаги

1. **Только заголовки.** Саммари размывает сходство и добавляет шумовые числа
(«90,46» склеилось с «91,46» по «46» из саммари).
2. **Очистка источниковых префиксов и мусора:**

- `Финам: Новости` / `Финам: Мировые рынки` — префикс в начале заголовка, стрипить;
- TG Parser News: эмодзи-флаги, `⚠️❗️💥`, хэштеги `#россия #дкп`, markdown `**жирный**`;
- нижний регистр, пунктуация → пробелы, схлопнуть пробелы.

3. **Сходство**: `0.5 · TF-IDF(слова, 1–2 граммы) + 0.5 · TF-IDF(char_wb, 3–5 грамм)`,
косинус.
4. **Окно по времени**: пары только в пределах 36 часов.
5. **Числовое вето** (ключевое правило): из заголовка извлекаются значимые числа
(≥2 знаков, исключая 2025–2027 как годы). Если у обоих заголовков есть числа и они
не пересекаются → НЕ дубль. Разделяет ежедневные шаблонные сводки («516» ≠ «494»).
6. **Склейка**: sim ≥ 0.40, или sim ≥ 0.30 + общее значимое число. Union-find по парам.
7. **Фильтр кластеров**: оставить только межисточниковые (≥2 разных source). Внутри-
источниковые цепочки (молнии одного Интерфакса) — не каскад, а поток апдейтов.
8. **Склейка между тегами**: один каскад находится через несколько тегов — мержить
кластеры с пересечением ≥2 новостей (или ≥50% меньшего).
9. **Разметка по силе** (для приоритизации ручной/LLM-проверки):

- сильный: max попарный sim ≥ 0.55, или общее число + sim ≥ 0.40;
- средний: sim ≥ 0.40 или общее число;
- сомнительный: остальное.
Калибровка показала: «средние» и «сомнительные» тоже преимущественно настоящие —
вердикт нужен для приоритета проверки, а не для отбраковки.

### Референс-код (Python)

```python
import re, numpy as np
from sklearn.feature_extraction.text import TfidfVectorizer
from datetime import datetime

def norm(t):
    t = (t or "").lower()
    t = re.sub(r'[^\w\s#%]+', ' ', t)
    return re.sub(r'\s+', ' ', t).strip()

def clean_title(t, source):
    t = t or ""
    if source.startswith("Финам"):
        t = re.sub(r'^финам:\s*(новости компаний|мировые рынки|новости|мировые)?\s*', '', t.lower())
    if source == "TG Parser News":
        t = re.sub(r'[#⚠️❗️💥⬆️*]+', ' ', t)
    return norm(t)

def sig_nums(t):
    return {x for x in re.findall(r'\d+', t) if len(x) >= 2 and x not in {'2025','2026','2027'}}

def ts(a):
    return datetime.fromisoformat(a["published_at"].replace("Z","+00:00")).timestamp()

def find_cascades(articles, gap_h=36, min_sim=0.40, num_floor=0.30):
    """articles: список новостей одного тега, отсортированный по published_at."""
    titles = [clean_title(a.get('title_ru') or a.get('title_original'), a['source']) for a in articles]
    sigs = [sig_nums(t) for t in titles]
    v1 = TfidfVectorizer(ngram_range=(1,2)).fit_transform(titles)
    v2 = TfidfVectorizer(analyzer='char_wb', ngram_range=(3,5)).fit_transform(titles)
    sim = ((v1 @ v1.T).toarray()*0.5 + (v2 @ v2.T).toarray()*0.5)
    n = len(articles); par = list(range(n))
    def find(x):
        while par[x] != x: par[x] = par[par[x]]; x = par[x]
        return x
    tt = [ts(a) for a in articles]
    for i in range(n):
        for j in range(i+1, n):
            if abs(tt[j]-tt[i])/3600 > gap_h: continue
            s = sim[i,j]
            if s < num_floor: continue
            vi, vj = sigs[i], sigs[j]
            if vi and vj and not (vi & vj): continue      # числовое вето
            if s >= min_sim or (vi and (vi & vj) and s >= num_floor):
                ri, rj = find(i), find(j)
                if ri != rj: par[ri] = rj
    groups = {}
    for i in range(n): groups.setdefault(find(i), []).append(i)
    # только межисточниковые кластеры
    return [g for g in groups.values()
            if len(g) >= 2 and len({articles[i]['source'] for i in g}) >= 2]
```

## 5. Классы ложных срабатываний (обязательные к обработке)

| Класс | Пример | Признак | Обработка |
| --- | --- | --- | --- |
| Рубрики-дайджесты | «Что произошло за день» Интерфакс/Известия, sim=0.98 | Идентичный шаблонный заголовок, разные даты | Чёрный список рубрик — самая опасная ложная склейка, выглядит уверенно |
| Шаблонные сводки МО | «Минобороны сообщило об ударе по…» ×6–8 молний | Один источник, один шаблон, разные объекты | Числовое вето (где есть числа) + LLM-верификация «тот же объект?» |
| Сюжетные склейки | 18 новостей «все встречи Путина на ШОС» | Кластер ≥8 новостей, жизнь >24ч | Двухуровневая модель: сюжет → разбиение на каскады через LLM |
| «Ложные друзья» — числа | «$90,46» vs «$91,46» склеились по «46» | Совпадение дробной части | Сравнивать числа как токены целиком, в идеале — семантику главного числа |
| Цепочки уровней | «Brent > $90» → «> $91» → «> $94» | Рыночные вехи, разные значения | Числовое вето; отдельный тип «рыночный поток», не каскад |
| Битые данные | Заголовки с утёкшим JSON промпта | sim≈1 на мусоре | Чинить баг в пайплайне перевода; детектор — как монитор |

## 6. Продакшен-архитектура (целевая)

```javascript
Новая новость получила тег
        │
        ▼ (асинхронно, очередь)
1. Нормализация заголовка (префиксы, TG-мусор)
2. Эмбеддинг заголовка → pgvector (HNSW), поиск top-10 за 48ч:
   SELECT ... WHERE published_at > NOW() - INTERVAL '48 hours'
   ORDER BY embedding <=> $1 LIMIT 10;
3. Трёхзонная логика по косинусу (пороги откалиброваны 2026-09-10 на
   calibration_pairs.csv: 3607 позитивных пар из импортированных кластеров +
   8277 негативных; максимум негативов 0.743, медиана дублей 0.80):
   ≥ 0.80  → автоприклеивание к кластеру кандидата (0 ложных склеек на выборке)
   0.55–0.80 → LLM-верификация пары (~130–200 вызовов/нед, дёшево)
   < 0.55  → новый seed-кластер
   (стартовые 0.92/0.80 были посчитаны под TF-IDF и не переносились)
4. Числовое вето — до LLM (бесплатный отсев; обязательно ДО трёх зон:
   на боевой БД 2026-09-11 сводки ПВО разных дней с разными числами дают
   sim до 0.944 — без вето авто-склейка слипала бы разные дни)
5. Приклеивание: news.cluster_id; clusters: size++, last_seen_at
```

Схема хранения:

```javascript
news:      + cluster_id (UUID, nullable)
clusters:  id, first_news_id, first_published_at, asset_ticker/tags[],
           size, last_seen_at, story_id (для двухуровневой модели)
stories:   id, title, started_at  — объединяет несколько каскадов одной истории
```

- GIN-индексы остаются на тегах (`idx_news_matched_tags` уже есть). GIN/trgm по тексту
для смыслового поиска бесполезны — переписанные заголовки лексически далеки.
- Эмбеддинг-модель: многоязычная — чтобы «Банк России» и «Центробанк» были близки.
- **Выбор модели (решение от 2026-09-10): `Qwen3-Embedding-0.6B`** — вершина
класса «CPU-моделей» (≤0,6 млрд параметров). Факты: ~1,2 ГБ веса (fp16),
dim 1024 (Matryoshka-обрезка до 32 при желании), контекст 32K токенов
(при появлении полных текстов статей модель менять не придётся), ~119 языков,
лицензия Apache-2.0 (коммерция ок). По качеству на многоязычных бенчмарках
бьёт e5-large при том же классе железа (64,3 против 63,2 балла MTEB).
- **Хостинг эмбеддингов — локально, GPU не нужен** (объёмы: ~1400 новостей/день,
короткие заголовки). Развёртывание для ТЗ: HF TEI (text-embeddings-inference)
или sentence-transformers + FastAPI в отдельном docker-контейнере на том же VPS,
~2–3 ГБ RAM на сервис. Сервис принимает `title_ru + " " + summary_ru`.
- Нюанс Qwen3: модели семейства заточены под instruction-префикс
(`Instruct: retrieve similar news passages\nQuery: ...`) — задаётся один раз
в конфиге сервиса, даёт прирост на retrieval-задаче.
- Колонка в pgvector: `news.embedding vector(1024)` (не 768 — это было под e5-base).
Смена модели = пересоздание колонки и полный пересчёт эмбеддингов: векторы
разных моделей между собой несравнимы.
- Backfill всей базы (119 тыс. новостей): ~2–4 часа CPU, разово. В проде —
единицы–десятки заголовков/сек, нагрузка копеечная.
- Запасные варианты: `multilingual-e5-base` (1,1 ГБ, dim 768, чуть слабее);
облегчённый `rubert-tiny2` (~120 МБ) — только RU. Апгрейд с GPU (не планируется):
Qwen3-Embedding-4B/8B — для коротких заголовков прирост микроскопический.
API-альтернатива без своего сервиса: gemini-embedding-001 / OpenAI
text-embedding-3-large — внешняя зависимость и оплата за токены.
- Объёмы: ~300–400 пар на LLM-верификацию в неделю на крупный тег — копейки.
- Инкрементальность: «всегда ищем в прошлое» — новая новость проверяется против окна
48ч, а не перекластеризация всей базы.
- **Минимум каскада = 2 новости** (решение владельца 2026-09-12). Обоснование
  данными: 70,7% всех каскадов полной базы — ровно пары (2–3 новости покрывают
  89,4%); порог 3 потерял бы семь из десяти событий. Продуктовый смысл: каскад
  = событие, кросс-подтверждённое минимум двумя независимыми источниками —
  встроенный фильтр достоверности. Одиночки не отбраковываются: при появлении
  второго источника в окне 48ч кластер «зажигается задним числом» с двумя
  новостями сразу (ТЗ-92, задача 2 п.6).

**Смысловые прогоны на боевой БД (2026-09-11, приёмка ТЗ-91 п.3):**
1. Ормуз/Иран: вся top-10 — одно событие другими словами, полоса 0.81–0.85,
   посторонних нет, дословных дублей нет — модель не «клеевая».
2. ПВО-сводки: разные дни/числа дают sim до 0.944 → числовое вето обязательно
   (ожидаемо: голый вектор числа не различает).
3. Дайджест «Что случилось этой ночью»: соседи — события ночи (0.77–0.79),
   шаблон другого дня лишь 0.695 → эмбеддинг title+summary пробивает шаблон;
   чёрный список рубрик всё равно оставляем (экономия вызовов верификатора).
4. Свежая новость (Tesla): чистая лесенка «перепечатка 0.729 → тема 0.55–0.61
   → индустрия ниже»; перепечатки ниже T1 уходят в LLM-зону — как задумано.

### 6.1 Формирование сюжетов (второй уровень модели)

**В эксперименте (факт):** сюжеты собраны кураторски — из 171 каскада недели
вручную выделены 5 сюжетов (генконсульство в Бонне, сводки ПВО, удары США ↔ Иран,
ралли Brent, ОФЗ-неделя Минфина). Алгоритмической группировки не было —
это эталонная разметка для калибровки.

**Целевая логика (для ТЗ):** сюжет = группа каскадов одной развивающейся истории.

1. Кандидаты: кластер ≥8 новостей **или** жизнь >24 ч (пороги из §5, класс
«сюжетные склейки»), либо несколько каскадов с пересечением по сущностям.
2. LLM-группировка (батч, дёшево): на вход — заголовок первой новости и
2–3 типичных дубля каждого каскада окна; задача — назначить каждому каскаду
`story_id` (существующий сюжет или новый). Промпт строится по конвенциям §9.1;
критерий «одна история» — общий предмет и причинная цепочка (сводки ПВО
ежедневные — ОДИН сюжет, хотя числа разные; закрытие консульства → ответ МИД —
ОДИН сюжет, хотя факты разные — зеркально критерию дубля §1).
3. Обратная задача — **разбиение** сюжетного кластера на каскады тем же
LLM-вызовом: «раздели эти N новостей на группы по отдельным фактам».
4. Метрики сюжета — те же §7, окно «первая новость первого каскада → последняя
новость последнего»; состав сюжета в детали — список входящих каскадов.
5. Пересмотр раз в час по cron достаточен: сюжеты медленные, онлайн-точность
не нужна.

### 6.2 Темы — третий уровень модели (реализовано)

> (env 7–30), прогон 03:40 МСК (хостовый cron VPS, one-shot через
> `--profile worker`), нейминг LLM 04:10 МСК (Node-cron, ≤1 вызов на новую
> тему в сутки), UI — вкладка «Темы» страницы «Каскады», только VPS-сборка.
> На Render тем нет (флаги `TOPICS_ENABLED` / `VITE_TOPICS_ENABLED`). Детали —
> `DEPLOYMENT.md` §«ТЗ-115» и `src/migrations/topics_v1.sql`.

Пирамида уровней (согласовано с владельцем 2026-09-12):

```
ТЕМА    недели–месяцы  «о чём гудит рынок»      HDBSCAN по векторам, 7–30 дн
СЮЖЕТ   дни–недели     «как развивается история» группа каскадов, LLM раз в час
КАСКАД  часы–сутки     «что произошло, кто первый» ≥2 новости, один факт
```

- **Зачем:** каскады-first имеет слепую зону — медленная тема без дублей
  (каждое издание пишет по разу и по-своему; пример: фоновая аналитика про
  госдолг США неделями) не порождает ни каскада, ни сюжета. Тематическая
  кластеризация работает прямо по эмбеддингам за длинное окно и ловит
  такие одиночные публикации.
- **Чем тема НЕ является:** не замена сюжета — у темы нет структуры «кто
  первый», нет причинной цепочки, размеры раздуты перепечатками. Это витрина
  фона, а не лента событий.
- **Реализация (проект):** раз в сутки HDBSCAN (или агломеративная) по
  эмбеддингам новостей за 7–30 дней; название темы — LLM по топ-заголовкам
  кластера; связь с сюжетами опциональна (тема ⊃ сюжеты по пересечению
  новостей). Стоимость — ноль LLM на кластеризацию, один вызов на название.
- **Когда делать:** после приёмки ТЗ-92 и недели наблюдения за чистотой
  каскадов; отдельным ТЗ, вкладка «Темы».

## 7. Метрики каскада (для UI/аналитики)

- Размер каскада (число дублей), время жизни (первая → последняя).
- Лаг первого дубля (медиана по ленте — 33 мин).
- Первоисточник + его first-rate (считать скользящим окном, не хардкодить).
- «Информационное отставание» источника: систематический медианный лаг.
Коммерсант 55 мин, Ведомости 37 мин — для трейдера такие источники вторичны.
- Дельта цены «первая новость → первый дубль» на графике актива.
- **Диапазон каскада/сюжета** (реализовано в мокапе): max − min цен закрытия свечей
в точках новостей + тот же диапазон в % от цены первой новости. Пример: цены в точках
100 / 102 / 100 → диапазон 2 → 2%. Выводится колонкой в таблицах и в шапке детали;
у каждой новости в списке под графиком показывается её цена (close свечи точки).
- **Волатильность каскада/сюжета** (реализовано в мокапе): σ лог-доходностей
5-минутных закрытий за окно «свеча первой новости → свеча последней», в % на бар.
Формула: `rets[i] = ln(close[i]/close[i-1])`, волатильность = выборочное
стандартное отклонение `rets` × 100. Особенность: на многодневных сюжетах σ
выравнивается (у всех сюжетов недели 0,12–0,13%/бар), на коротких каскадах
разброс информативен (0,03–0,34%/бар). Если для сюжетов нужна различительная
сила — считать σ только в окнах активности вокруг новостей, а не за весь период.

### 7.1 Топ-карточки «интересные события» (над таблицами, реализовано в мокапе)

Три карточки над таблицей каскадов и над таблицей сюжетов; клик открывает
детальную панель записи. Формальные определения (считаются по текущему набору
записей вкладки):

| Карточка | Метрика | Формула | Пример недели |
| --- | --- | --- | --- |
| Самый длинный | Время жизни | max(`published_at` последней − `published_at` первой новости) | Сюжет «Ежедневные сводки ПВО» — 161 ч; каскад «Google Maps» — 62,3 ч |
| Самый виральный | Размер | max(число новостей в кластере) | «Минфин / ОФЗ» — 7 новостей в каскаде |
| Самый волатильный | σ | max(волатильность по формуле §7) | Каскад «МИД РФ / Япония» — 0,34%/бар |

В карточке выводится: значение метрики крупно, название записи, мета-строка
(число новостей · период · диапазон). Кандидаты на расширение набора
(обсуждено, не реализовано): «самый быстрый» (min лаг первого дубля),
«максимальный диапазон %», «самый ленивый» (max медианный лаг дублей).

## 8. Визуализация каскада на графике (мокап)

Собран HTML-мокап (`app/index.html` + `app/data.js`, вход — `index.html`):
вкладки «Каскады» / «Сюжеты» / «Ресерч: кто первый» / «Методология»; таблицы
каскадов и сюжетов с сортировкой кликом по шапке (первый клик — по убыванию,
второй — по возрастанию); топ-карточки над таблицами («самый длинный» /
«самый виральный» / «самый волатильный», клик открывает деталь); клик по строке
открывает свечной график инструмента с точками новостей и список новостей
под графиком. Переключение вкладки закрывает детальную панель (иначе открытый
график маскирует смену вкладки — поймано на ревью 05.09). Дизайн — по
`Дизайн-система_PULSE.md` (тёмная тема, glassmorphism, акцент #00D4FF).
Пока для всех каскадов используется один инструмент — IMOEXF@RTSX.

### Данные свечей

- Источник: публичный MOEX ISS (Finam Trade API недоступен без JWT):
`iss/engines/futures/markets/forts/securities/IMOEXF/candles.json?interval=1`,
пагинация по 500 строк, агрегация 1-мин → 5-мин.
- Итого 1256 пятиминуток за 29.08–05.09.2026.
- **Выходные сессии разрежены**: 30.08 (воскресенье) первая свеча только в 09:55 —
бакеты без сделок отсутствуют в данных, это норма, а не дыра выгрузки.
- Формат в `data.js`: свеча = массив `[время_строкой_MSK, open, close, low, high, vol]`
(порядок o,c,l,h — формат ECharts candlestick). Время новостей в каскадах — ISO UTC
(`...T06:16:43.000Z`).

### Маппинг новости на график

1. `published_at` (UTC) → MSK: `+3ч` на миллисекундах, далее только UTC-геттеры.
2. Округление вниз до 5-минутного бакета → ключ `YYYY-MM-DD HH:MM`.
3. Точное совпадение ключа со свечой → маркер на свече.
4. Бакета нет (вне сессии / нет сделок) → **ближайшая свеча диапазона**, маркер
рисуется пустым кружком + пометка «вне сессии» в тултипе.
5. Диапазон графика: все свечи от дня первой новости до дня последней, единый
многодневный график, границы дней — вертикальные markLine.
6. Первая новость — циановый пин «1» (первоисточник, #00D4FF по дизайн-системе),
дубли — пронумерованные точки, размер убывает с порядковым номером.

### Состав детальной панели (что рендерится по клику)

1. **Заголовок**: тип записи + факт первой новости («Каскад · …» / «Сюжет: …»).
2. **Мета-строка**: число новостей · число источников · жизнь · инструмент ·
шаг свечей · время MSK · **диапазон** (абс. и % от цены первой новости) ·
**волатильность** (%/бар).
3. **График** (ECharts candlestick): свечи диапазона + scatter-маркеры новостей
(пин/точки/пустые кружки «вне сессии»), markLine границ дней, dataZoom-слайдер.
Тултип маркера: время МСК, источник, заголовок, **цена** (close свечи точки),
лаг от первой новости.
4. **Список новостей под графиком**: порядковый номер, время МСК, источник,
заголовок (ссылка), цена в точке, бейдж «первоисточник» или лаг «+N мин».

Данные для панели в боевой версии — один ответ эндпоинта `cluster-chart`
(§11.8): массив свечей диапазона + массив новостей каскада + посчитанные
на сервере метрики §7. В мокапе всё это предрасчитано в `data.js`.

### Вкладка «Граф» — новостное пространство (мокап, 05.09)

Карта каскадов и сюжетов как граф (ECharts graph, force layout):

- **Узел = новость.** Крупный с белой обводкой — первоисточник, мелкие — дубли
(размер убывает с номером).
- **Сплошная цепочка** — порядок перепечаток внутри каскада.
- **Цвет = сюжет** (палитра дизайн-системы), серое — каскады вне сюжетов.
Легенда-категории кликабельна (можно гасить сюжеты).
- **Пунктир** — новость сюжета, не попавшая ни в один детектированный каскад,
привязана к «хабу» сюжета (первой его новости, вошедшей в каскад).
- Клик по узлу — детальная панель каскада/сюжета; roam/zoom.
- **Фон — вся лента**: 9 442 одиночки (все новости недели минус узлы графа)
отрисованы статичным «звёздным полем» на canvas под графом, ось X = время
с суточной сеткой. Именно статичным: 10k узлов в force layout — это O(n²) на
тик симуляции, браузер умрёт; фоновый канвас бесплатен. Минус: фон не
масштабируется при зуме графа (помечено в подсказке под графом).
Данные фона — отдельный `feed.js` (961 КБ, компактный массив [ts, источник,
заголовок]), чтобы не раздувать `data.js`.

**Наблюдение по данным (важно для оценки recall):** из 171 каскада к сюжетам
привязаны только 17, а 122 из 154 новостей сюжетов не входят ни в один каскад —
на графе сюжеты выглядят «звёздами» из пунктирных спутников. Это наглядный
монитор полноты детектора: по мере роста recall пунктир должен превращаться
в сплошные цепочки.

**Ограничение для прода:** в мокапе 529 узлов — force layout справляется.
Полный поток (10k новостей/неделя) в браузер отдавать нельзя: эндпоинт должен
отдавать только узлы кластеров за окно 24–72 ч (+опционально одиночки фоном),
связи — готовым списком `cluster_id`, а не вычисляться на клиенте.

### Ловушка часовых поясов (поймано на мокапе, 05.09)

Нельзя сравнивать строковое московское время свечи через браузерный `new Date(str)`:
он парсит строку в **часовом поясе браузера пользователя**. Если сравнивать такое
значение с `published_at + 3ч`, шкалы совпадают только в браузере с UTC; у пользователя
в UTC+5 все «внесессионные» маркеры смещались ровно на 5 часов (09:16 → 14:15).
Правило: строковое wall-clock время разбирать вручную через
`Date.UTC(y, m-1, d, H, M)` — тогда результат не зависит от таймзоны браузера.
Проверено прогоном логики в зонах UTC / Europe/Moscow / Asia/Yekaterinburg —
после фикса позиции маркеров идентичны во всех трёх.
**При написании боевого ТЗ проверить `TagMarketTimeline.tsx` на ту же зависимость.**

### 9.3 Баг утечки промпта в title_ru — root cause подтверждён

Симптом из §2.5 (сырой JSON промпта в `title_ru` у OilPrice.com/MarketWatch).
Причина в `translate.ts`:

1. `response_format: {type:'json_object'}` (`:105`) противоречит инструкции
«Return ONLY a JSON array» — провоцирует k2.6 отвечать объектом.
2. Ветка парсинга объекта (`:152-172`) берёт `Object.values(parsedObj)` с фильтром
только по типу string. k2.6 изредка возвращает эхо запроса
(`{"prompt":"You are a senior financial news editor...", "0":"...", ...}`) —
строка-эхо промпта проходит фильтр и сохраняется как перевод → утечка в title_ru.

Фикс подготовлен (`/mnt/agents/output/translate_fix.ts`, 04.09): фильтр
`isGarbage()` (отбраковка строк, начинающихся с `{`/`[`, содержащих
«senior financial news editor» / «Translate these», длины <2 или >300) во всех
трёх ветках парсинга + снятие `response_format`. **В снапшоте кода не применён**
(`src/services/translate.ts` по-прежнему без фильтра) — отдельное ТЗ.

### 9.4 Проект промпта LLM-верификатора каскадов (для ТЗ)

Критерий и контрпримеры — из §1. Конвенции — как в §9.1 (user-only,
json_object, thinking disabled, temp 0.6, timeout 30 с, max_tokens ~150):

```text
Ты — редактор новостной ленты PULSE. Определи, сообщают ли две новости
ОДИН И ТОТ ЖЕ ключевой факт.

Новость A: «{title_a}» ({source_a}, {published_a})
Новость B: «{title_b}» ({source_b}, {published_b})

Дубль = тот же факт без существенно новой информации.
НЕ дубли (контрпримеры):
- одно событие, разные новости («Сбер отчитался» ≠ «Аналитики про отчёт Сбера»);
- один брифинг, разные тезисы;
- шаблонные сводки с разными числами («85 дронов» ≠ «516 дронов»);
- развитие истории (закрытие консульства → ответ МИД — разные факты);
- рыночные вехи с разными значениями («Brent > $90» ≠ «Brent > $94»).

Ответь строго JSON:
{"same_fact": true|false, "confidence": 0.0-1.0, "reason": "1 предложение на русском"}
```

Вызывается только для пар в серой зоне эмбеддингов (косинус 0.80–0.92, §6)
после числового вето. Ожидаемая нагрузка — 300–400 вызовов в неделю на
крупный тег (копейки по §6).

## 10. Ограничения эксперимента

- 7 дней данных, published_at из RSS = время попадания в нашу ленту, а не обязательно
время публикации у источника (особенно TG Parser — возможен лаг парсера; его
бимодальность «либо первый, либо +2,5ч» требует сверки с реальными постами).
- Recall неизвестен: эвристика не ловит полностью переписанные заголовки без общих слов.
- Новости без тегов не анализировались.
- Ручная верификация выборочная (топ-кластеры + случайные выборки по вердиктам).

   инструментом (`:122`, TZ-3.4);
   - свечи 5-мин за день публикации; вне сессии → ближайший торговый день +
   флаг `shifted: true`; таймзона биржи через `exchangeTimezones.ts`
   (та же ловушка таймзон из §8 уже решена на сервере);
   - in-memory кэш: TTL 60 с для «сегодня», 24 ч для прошлых дней, 15 мин для
   пустых, max 5000 ключей с eviction 20% (`:17-30`);
   - данные через `marketRouter.getIntraday5min(ticker, date)` → MOEX ISS /
   Finam (`services/market/marketRouter.ts:53`).
   Отличия cluster-chart от news-chart: ключ `cluster_id` вместо `news_id`;
   диапазон «день первой → день последней новости» — ⚠️ `getIntraday5min`
   принимает **один день** (`moexIssAdapter.ts:238`), для многодневных каскадов
   нужен цикл по дням (в мокапе: пагинация ISS по 500 1-мин свечей + агрегация
   в 5-мин); в ответ добавить массив новостей каскада `{time, source, title,
   url, lag_min}` и посчитанные метрики §7 (диапазон, %, волатильность).
