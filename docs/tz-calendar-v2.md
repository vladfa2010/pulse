# ТЗ: Блок «Календарь инвестора» на главной

**Версия 2.1** · 2026-08-30 · история изменений — в конце документа

> Отдельный блок главной страницы. Без переключателя «Дайджест/Календарь» —
> самостоятельная секция с собственным заголовком.
> Данные: Investmint, Smartlab и другие провайдеры (отчётности РСБУ/МСФО, советы директоров, собрания акционеров, дивиденды). Сырые снапшоты нормализуются адаптерами и сливаются в единую canonical-таблицу.
> Стек: React 19 + TS + Tailwind + Framer Motion + Lucide / Node.js + Express + PostgreSQL.

---

## 1. Цель

Дать пользователю ответ на вопрос «что ещё будет сегодня (и дальше) по рынку и по моему портфелю» — в дополнение к Дайджесту, который отвечает на вопрос «что уже произошло».

**Размещение:** главная (`Home.tsx`), сразу после секции `DailySummary`, до `UnreadNewsCarousel`. Виден всем пользователям (в т.ч. гостям); подсветка «в портфеле» — только залогиненным с тегами.

## 2. UX и внешний вид

### 2.1 Структура блока

```
┌────────────────────────────────────────────────────────┐
│ [▦] Календарь                    Обновлено 09:40  ⟳    │  ← шапка (как у DailySummary)
│     Отчётности и события по рынку · Investmint         │
├────────────────────────────────────────────────────────┤
│ [пн 24] [вт 25] [СР 26●] [чт 27] [пт 28] [сб 29] ...   │  ← лента дат (горизонт. скролл)
│                                                        │
│ 26 авг, среда [СЕГОДНЯ]         2 события · 15 эмитентов · 1 ваших │
│ ┌──────────────────────────────────────────────────┐   │
│ │ [МСФО] МСФО за 2 КВ 2026 ожидается   (ожидается) │   │
│ │  • Завод ДИОД                            DIOD    │   │
│ │  • Россети Сибирь                        MRKS    │   │
│ └──────────────────────────────────────────────────┘   │
│ ┌──────────────────────────────────────────────────┐   │
│ │ [СД] Заседание совета директоров   (подтверждено)│   │
│ │  ● Норникель [в портфеле]                GMKN    │   │
│ │  ...                              ещё 5 ▾        │   │
│ └──────────────────────────────────────────────────┘   │
│ ожидается = прогнозная дата · данные обновляются еженедельно │
```

### 2.2 Шапка

- Иконка `CalendarDays` (Lucide) в градиентном квадрате — как у DailySummary (`linear-gradient(135deg, rgba(0,212,255,0.15), rgba(52,211,153,0.1))`, бордер `rgba(0,212,255,0.2)`)
- Заголовок «Календарь» (18px, semibold) + подпись (12px, `#6B7280`)
- Справа: время обновления данных (`generated_at` от бэкенда) + кнопка «Обновить» (`RefreshCw`, стили кнопки DailySummary). Кнопка делает `invalidateQueries(['calendar'])`

### 2.3 Лента дат

- Горизонтальный скролл (`scrollbar-hide`), drag-scroll мышью, свайп на таче
- Чип даты 58px: день недели (10px uppercase), число (17px bold), до 3 цветных точек по типам событий
- Выходные (`сб`, `вс`) — приглушённый цвет числа `#5b6472`
- Сегодня — бордер `rgba(0,212,255,0.45)`, cyan текст
- Выбранный день — фон `rgba(0,212,255,0.12)`, бордер `#00D4FF`, glow `0 0 14px rgba(0,212,255,0.25)`
- Если в дне есть событие по тикеру из портфеля — градиентная риска под чипом (`linear-gradient(90deg,#00D4FF,#34D399)`)
- При открытии блока лента автоскроллится так, чтобы выбранный день был в центре

### 2.4 События дня

- Заголовок: «26 авг, среда» + бейдж «СЕГОДНЯ» (если выбран server_date) + счётчик «N событий · M эмитентов · K ваших»
- Группа события = карточка `rgba(255,255,255,0.018)`, бордер `rgba(255,255,255,0.05)`, radius 12px:
  - Чип типа: **МСФО** cyan / **РСБУ** `#A78BFA` / **СД** `#FBBF24` / **Другое** серый (цвета — из DESIGN_SPEC: company/sector/person)
  - Название события (13.5px semibold)
  - Статус справа: «ожидается» (warning `#F59E0B`) / «подтверждено» (success `#34D399`)
  - Строки компаний: точка, название, тикер справа (tabular-nums)
- Более 6 компаний в группе — сворачиваются, кнопка «ещё N ▾» → раскрытие с анимацией, «свернуть»
- Совпадение с портфелем: фон строки `rgba(0,212,255,0.05)`, cyan точка с glow, бейдж «в портфеле»

### 2.5 Состояния

| Состояние | Поведение |
|---|---|
| Загрузка | Skeleton в стиле DailySummary (полосы + чипы дат) |
| Ошибка API | Иконка `AlertCircle` + «Не удалось загрузить календарь» + кнопка «Повторить» |
| Снапшот не загружен (`503 calendar_not_loaded`) | Блок скрыт для обычных пользователей и гостей; placeholder «Данные календаря пока не загружены» виден только админам |
| Пустой день | «На этот день событий нет» (14px, `#6B7280`) |
| Сегодня без событий | Блок открывается на ближайшем будущем дне; над списком плашка «Сегодня событий нет — ближайшие:» |
| Данные протухли (`stale: true`) | Жёлтая плашка «Данные устарели» (файл не покрывает актуальную дату — см. 5.4) |

### 2.6 Анимации

- Вход блока: `opacity 0→1, y 24→0`, 0.6s, `easeOutExpo [0.16,1,0.3,1]`
- Группы событий: каскад `delay: index * 0.06`
- Смена дня: контент перерендеривается с `fade+y 8px`, 0.3s

### 2.7 Фильтры по типу события

- Ряд чипов **«Все · МСФО · РСБУ · СД · СА · Дивиденды · Другое»** между лентой дат и заголовком дня — полный набор типов Investmint. Цвета точек — из 2.4. На узких экранах ряд чипов скроллится горизонтально (`scrollbar-hide`), не переносится
- Стили — как у Tag: pill, цветная точка типа, активный чип — заливка цвета типа с opacity 12% + бордер
- Фильтруются: список групп дня **и** счётчик «N событий · M эмитентов»
- Чип даты, в котором нет событий выбранного типа, приглушается (opacity 40%), но остаётся кликабельным; точки на чипах показывают только типы из активного фильтра
- Выбранный фильтр сохраняется в `localStorage` (`pulse_calendar_filter`) и восстанавливается при следующем визите
- «Все» — состояние по умолчанию
- Если для дня после фильтрации пусто — empty state «Событий этого типа нет»

### 3.2а Связка «теги ↔ события» (без LLM, v1)

Событие календаря всегда имеет название компании и тикер — матчим теги пользователя напрямую, без LLM-обогащения. Функция `src/lib/calendarMatch.ts`:

```typescript
matchPortfolio(companies: CalendarCompany[], portfolio: PortfolioTag[]): Set<string> // → Set тикеров «моих» компаний
```

**Правила матчинга (применяются по порядку, нормализация: lowercase, trim, убрать кавычки и «ПАО»/«АО»):**

1. **Точное совпадение по тикеру**: `tag_id.toUpperCase() === company.ticker` (тег `sber` ↔ тикер `SBER`)
2. **Точное совпадение по названию**: нормализованный `tag_name` === нормализованный `company.name` (тег «Сбербанк» ↔ «Сбербанк»)
3. Подстроки и нечёткие совпадения — **запрещены в v1** (ложные срабатывания вида «СПб Биржа» ↔ «Банк СПб» недопустимы в платном продукте)

**Осознанные ограничения v1:** пользовательский тег «сбер» или «т-банк» не совпадёт — промах допустим, ложное совпадение — нет. Метрика качества: доля company-тегов пользователей, для которых найдено совпадение (логируется в аналитику); если окажется низкой — v2: LLM-обогащение тегов тикером при создании.

- Компонент внутри вызывает `matchPortfolio` (memo по `portfolio` и выбранному дню) → подсветка «в портфеле» + риски на чипах дат + счётчик «K ваших»

### 3.3 Данные и «сегодня»

- «Сегодня» — **только `server_date` из ответа бэкенда** (МСК). Клиентские часы/таймзона не используются
- React Query (паттерн PopularTagsSlider):

```typescript
const { data, isLoading, isError } = useQuery({
  queryKey: ['calendar'],
  queryFn: () => api.get('/calendar'),
  staleTime: 5 * 60 * 1000,
  gcTime: 30 * 60 * 1000,

```

- Стартовый выбранный день: `server_date`, если на него есть события; иначе ближайший будущий день; иначе последний доступный
- Инвалидация по SSE-событию `calendar:refresh` (реиспользовать `useSseNews`-канал), когда бэкенд обновил данные источника

## 4. API-контракт

### `GET /api/calendar`

Авторизация не требуется (блок публичный). Персонализация («в портфеле») считается на фронте.

**Ответ 200:**

```json
{
  "server_date": "2026-08-26",
  "generated_at": "2026-08-26T06:40:00.000Z",
  "stale": false,
  "days": [
    {
      "date": "2026-08-26",
      "weekday": "ср",
      "groups": [
        {
          "title": "МСФО за 2 КВ 2026 ожидается",
          "kind": "МСФО",
          "status": "expected",
          "companies": [
            { "name": "Завод ДИОД", "ticker": "DIOD" },
            { "name": "Россети Сибирь", "ticker": "MRKS" }
          ]
        }
      ]
    }
  ]
}
```

**Поля:**

| Поле | Тип | Описание |
|---|---|---|
| `server_date` | `YYYY-MM-DD` | «Сегодня» по МСК — единственный источник правды о текущей дате |
| `generated_at` | ISO 8601 UTC | Когда бэкенд обновил данные источника → «Обновлено HH:MM» в шапке |
| `stale` | bool | `true`, если последний парсинг источника неудачен и данные устарели |
| `days[]` | array | Только дни с событиями, от `server_date - 2 дня` до `+120 дней`, отсортированы по дате |
| `kind` | enum | `МСФО` / `РСБУ` / `СД` / `Другое` |
| `status` | enum | `expected` (в названии есть «ожидается»/«предварительно») / `confirmed` |

**Кэш:**
- Серверный in-memory кэш: `TTL 60 с`, инвалидация при любой мутации снапшота (replace/merge) и при CRUD событий. Кэш позволяет обрабатывать публичный `GET /api/calendar` без обращений к БД в течение минуты после первого запроса.
- HTTP-заголовок `Cache-Control: public, max-age=300` (без CDN на Render не даёт эффекта, но сохранён для совместимости).
- React Query — `staleTime: 5m`, `refetchOnWindowFocus: true`.

**TypeScript (types/calendar.ts):**

```typescript
export type EventKind = 'МСФО' | 'РСБУ' | 'СД' | 'СА' | 'Дивиденды' | 'Другое'
export type EventStatus = 'confirmed' | 'expected'

export interface CalendarCompany { name: string; ticker: string }
export interface CalendarEventGroup {
  title: string
  kind: EventKind
  status: EventStatus
  companies: CalendarCompany[]
}
export interface CalendarDay {
  date: string        // YYYY-MM-DD
  weekday: string     // 'пн'..'вс'
  groups: CalendarEventGroup[]
}
export interface CalendarResponse {
  server_date: string
  generated_at: string
  stale: boolean
  days: CalendarDay[]
}
```

## 5. Backend

### 5.0 Решение по данным (v2)

**Без парсера.** Данные загружаются вручную готовым JSON-файлом (формат `CalendarDay[]`, см. раздел 4) через админку. Парсинг Investmint/Smartlab, cron и мониторинг источника — в бэклог v3.

**Двухслойная модель данных.** С версии 2.0 календарь хранится в двух слоях:
- **Raw-срезы** (`calendar_events_raw`) — всё, что загружено от каждого провайдера/источника, плоским списком. Источник указывается в поле `source`.
- **Canonical** (`calendar_events`) — результат автоматического слияния raw-строк по ключу `(date, ticker)` (или `(date, нормализованное название)` для тикеров `UNKNOWN`). Это единая, дедуплицированная картина, которую отдаёт `GET /api/calendar`.

**Почему двухслойная модель:** разные провайдеры (Investmint, Smartlab, BCS и др.) дают разную полноту по одним и тем же событиям. Вместо того чтобы последний снапшот затирал предыдущий, мы накапливаем срезы и склеиваем их в canonical-таблицу. Приоритет источников: `manual > investmint > smartlab > bcs > global > legacy` — если одно и то же событие пришло от нескольких источников, representative (заголовок, статус) берётся от источника с наивысшим приоритетом. `legacy` поглощается, если появился любой живой источник.

**Адаптеры провайдеров (M2).** Каждый провайдер отдаёт события в своём формате. Перед записью в `calendar_events_raw` сырые данные проходят через модуль `src/services/calendarAdapters/`:
- `CalendarAdapter` — единый интерфейс: `source`, `detect(raw)` (score 0–1), `parse(raw) → { events, warnings }`;
- `classify.ts` — общая функция `detectKind(title)` и `detectStatus(title)`, общая для фронта и бэка;
- `dateUtils.ts` — парсинг дат, эвристика года, вычисление дня недели;
- `investmint.ts` — адаптер для «дата + массив строк событий» с внутренним разбором тикера;
- `smartlab.ts` — адаптер для массива объектов `{ date, title }` с префиксом тикера `TICKER: title`;
- `bcs.ts` — заглушка-контракт для будущего BCS-источника;
- `detectAdapter(raw)` в `index.ts` выбирает адаптер по максимальному score, отклоняет неуверенные и неоднозначные семплы.

`parse()` возвращает `NormalizedEvent[]` — промежуточный формат, не зависящий от источника. Функция `toRawRows(events, source)` разворачивает события в плоские raw-строки `(source, date, weekday, title, kind, status, company, ticker)`, которые затем пишутся в `calendar_events_raw` и пересобираются в canonical (см. 5.5).

**Рекомендуемый ритм обновления — раз в неделю** (удобно: в воскресенье, вместе с еженедельным репортом). Обоснование: статус «ожидается» имеет значение только для будущих дат — событие, которое «ожидалось сегодня», завтра уходит в прошлое и перестаёт быть видимым. Ручная загрузка поддерживает любую частоту без доработок; если по факту понадобится ежедневная свежесть «без рук» — повышаем приоритет автопарсера из v2.

**Почему не файл на диске и не `public/` фронта:**
- Файл в `public/` фронтенда → «сегодня» пришлось бы считать на клиенте (нарушает правило server_date) + каждое обновление = редеплой
- Файл на диске backend → у Render эфемерная ФС, файл теряется при рестарте/редеплое
- Поэтому: **снапшот в базе**, обновление через админ-эндпоинт без редеплоя

### 5.1 Загрузка файла (админ)

- `POST /api/admin/calendar?mode=<replace|merge>` (защита существующим `adminMiddleware`)
  - `replace`: удаляет raw-срез `source = 'legacy'` и записывает новый файл в `calendar_events_raw` с `source = 'legacy'`, затем пересобирает canonical-таблицу.
  - `merge` (режим по умолчанию в UI): добавляет новый legacy-срез поверх старых raw-строк, затем пересобирает canonical. Существующие группы в canonical не трогаются напрямую; дедупликация происходит на этапе rebuild.
- Body: `{ "days": CalendarDay[] }` — JSON целиком. Лимит `express.json` поднят до **5 МБ**, чтобы вмещать полные снапшоты от разных провайдеров.
- Валидация: массив непустой, у каждого дня `date` формата `YYYY-MM-DD`, `weekday`, непустой `groups`; у групп — `title`, `kind`, `status`, `companies[]` с `name`+`ticker`
- После коммита — broadcast SSE-события `calendar:refresh` (новый тип события в существующем канале, payload пустой): всем открытым клиентам → `invalidateQueries(['calendar'])`. Отдельный тип, а не переиспользование новостного refresh с фильтром по payload — контракт чище, подписчики не пересекаются
- Фронт админки: модалка «Загрузка снапшота» с выбором файла, предпросмотром (дни / события / компании / период) и радио-кнопками режима `merge`/`replace` (merge по умолчанию).

### 5.2 Хранение

**Canonical-таблица** `calendar_events` — результат слияния, отдаётся в API:

```sql
CREATE TABLE calendar_events (
  id                  UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  date        DATE NOT NULL,
  weekday     VARCHAR(2) NOT NULL,
  title       TEXT NOT NULL,
  kind        VARCHAR(10) NOT NULL,      -- МСФО | РСБУ | СД | СА | Дивиденды | Другое
  status      VARCHAR(10) NOT NULL,      -- expected | confirmed
  company     VARCHAR(100) NOT NULL,
  ticker      VARCHAR(10) NOT NULL,
  uploaded_at TIMESTAMP DEFAULT NOW(),
  sources     TEXT,                      -- JSON ["investmint",...]
  possible_duplicate BOOLEAN DEFAULT FALSE,
  tag_ids     TEXT,                      -- заполняется в М6
  UNIQUE (date, title, kind, ticker)
);
CREATE INDEX idx_calendar_events_date ON calendar_events(date);
```

**Raw-срезы** `calendar_events_raw` — всё, что пришло от провайдеров:

```sql
CREATE TABLE calendar_events_raw (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source      VARCHAR(20) NOT NULL,        -- 'investmint' | 'smartlab' | 'legacy' | 'manual'
  date        DATE NOT NULL,
  weekday     VARCHAR(2) NOT NULL,
  title       TEXT NOT NULL,
  kind        VARCHAR(10) NOT NULL,
  status      VARCHAR(10) NOT NULL,
  company     VARCHAR(100) NOT NULL,
  ticker      VARCHAR(10) NOT NULL,
  uploaded_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_cal_raw_source ON calendar_events_raw(source);
CREATE INDEX idx_cal_raw_key ON calendar_events_raw(date, ticker);
```

**Источники** `calendar_sources` — метаинформация по каждому провайдеру:

```sql
CREATE TABLE calendar_sources (
  source              VARCHAR(20) PRIMARY KEY,
  uploaded_at         TIMESTAMP,
  last_stale_alert_at TIMESTAMP
);
```

**Метаданные снапшота** — однострочная таблица `calendar_meta` (`id INTEGER PRIMARY KEY CHECK (id = 1)`, `uploaded_at TIMESTAMP`, `last_stale_alert_at TIMESTAMP`). `generated_at` в API = `uploaded_at` отсюда.

### 5.3 Эндпоинт

- `src/routes/calendar.ts` → `GET /api/calendar`
- Публичный эндпоинт читает **canonical-таблицу** `calendar_events`, а не raw-срезы. Использует серверный in-memory кэш (`services/calendar.ts`): если ответ свежий (≤60 с), возвращается закэшированный `CalendarResponse` без запросов в БД. При промахе кэша проверяется `calendar_events`, затем выполняется **один плоский запрос** + группировка в памяти (без N+1, без диалектного SQL):

```sql
SELECT date, weekday, title, kind, status, company, ticker
FROM calendar_events
WHERE date BETWEEN (server_date - 2 дня) AND (server_date + 120 дней)
ORDER BY date, title;
```

Далее сборка `days[] → groups[] → companies[]` в JS за O(n) через Map. Объём — единицы тысяч строк, производительности хватает с запасом; запрос переносим между SQLite (dev) и Postgres (prod). SQL-side агрегацию (`json_agg` в Postgres / `json_group_array` в SQLite ≥3.38) сознательно **не** используем в v1: вложенная агрегация «дни → группы → компании» потребовала бы двух разных диалектных запросов на поддержке. Опция на будущее — если снапшот вырастет на порядок
- `server_date`: `NOW() AT TIME ZONE 'Europe/Moscow'`, формат `YYYY-MM-DD` — подставляется при каждом запросе
- Если таблица пустая (файл ещё не загружали) — `503 { "error": "calendar_not_loaded" }`; фронт в этом случае **не рендерит блок вовсе**, кроме администраторов, которым показывается placeholder с подсказкой загрузить снапшот

### 5.4 Протухание данных (stale)

- `stale: true`, если в данных **нет ни одного дня ≥ server_date − 2 дня** (т.е. снапшот перестал покрывать актуальную дату — пора заливать свежий файл)
- Фронт при `stale: true` показывает жёлтую плашку «Данные устарели» (см. 2.5), но события всё равно рендерит
- Дополнительно: при `stale: true` — одноразовый алерт админу в Telegram (существующий бот-канал), чтобы не забыть залить файл

### 5.5 Сборка canonical (rebuildCanonical)

После любой мутации raw-слоя (`replace`, `merge`, CRUD-событий, ручного добавления) запускается `rebuildCanonical()`:

1. Читает `calendar_events_raw` одним `SELECT`.
2. Группирует строки по `(date, ticker)` (для `UNKNOWN`-тикеров — по нормализованному названию компании).
3. Внутри группы разделяет по `kind`. Если одно событие оказалось в нескольких `kind`, каждый kind выводится отдельной canonical-строкой с `possible_duplicate = true`.
4. Выбирает representative для `(kind, date, ticker)` по приоритету источника, длине названия, алфавиту. Заголовок, статус и компания берутся от representative.
5. Статус `confirmed` имеет приоритет над `expected` внутри одного kind.
6. `sources` — дедуплицированный JSON-массив источников; `legacy` удаляется, если есть любой другой источник.
7. Записывает результат в `calendar_events` (`DELETE` + `INSERT`), инвалидирует in-memory кэш и рассылает SSE `calendar:refresh`.

**Миграция:** при старте бэкенд вызывает `runCalendarV2Migrations()`. Она:
- заменяет старый `UNIQUE (date, title, ticker)` на `UNIQUE (date, title, kind, ticker)`;
- мигрирует существующие строки `calendar_events` в `calendar_events_raw` со `source = 'legacy'`;
- добавляет источник `legacy` в `calendar_sources`;
- пересобирает canonical.

### 5.6 Адаптеры провайдеров (`src/services/calendarAdapters/`)

Модуль изолирует знание о форматах конкретных провайдеров. Задача адаптера: принять сырой JSON от источника и вернуть `NormalizedEvent[]` — единый промежуточный формат, который затем разворачивается в `calendar_events_raw` через `toRawRows()`.

**Файлы:**

```
src/services/calendarAdapters/
  types.ts       — CalendarAdapter, NormalizedEvent, NormalizedCompany, ParseWarnings
  classify.ts    — detectKind(title), detectStatus(title)
  dateUtils.ts   — pad, inferYear, getWeekday, toDateString
  investmint.ts  — адаптер investmint
  smartlab.ts    — адаптер smartlab
  bcs.ts         — заглушка BCS
  index.ts       — registry, detectAdapter(), toRawRows()
```

**`CalendarAdapter`:**

```typescript
export interface CalendarAdapter {
  source: string
  detect(raw: unknown): number   // 0..1, уверенность
  parse(raw: unknown): { events: NormalizedEvent[]; warnings: ParseWarnings }
}
```

**`detect(raw)`** оценивает, подходит ли файл адаптеру. Пример scoring:
- `investmint`: первые 3 элемента; +0.5 за `date` вида `«28 августа ср»`, +0.5 за поле `events: string[]`;
- `smartlab`: первые 3 элемента; +0.5 за `date` вида `DD.MM.YYYY`, +0.5 за `title` строка.

Файл признаётся подходящим, если `score >= 0.5`. `detectAdapter()` выбирает лучший score; если лучшие два score отличаются менее чем на 0.001 — семпл считается неоднозначным и отклоняется.

**`parse(raw)`** возвращает:

| Поле | Описание |
|---|---|
| `events[]` | Нормализованные события с `date`, `weekday`, `title`, `kind`, `status`, `companies[]` |
| `warnings.noTicker` | Количество событий без распознанного тикера (smartlab: ticker → `UNKNOWN`) |
| `warnings.skipped` | Строки, которые не удалось распарсить (investmint) |
| `warnings.invalidDates` | Элементы с нераспознанной датой |
| `warnings.details` | Человекочитаемые сообщения для отладки |

**Правила классификации (`classify.ts`)** применяются единообразно на бэке и фронте:
- `СД`: «совет директоров» или отдельное слово «сд»;
- `СА`: «госа», «воса», «собрание акционеров» или слово «собрание»;
- `МСФО` / `РСБУ` по вхождению;
- `Дивиденды`: только после проверки СД, чтобы «СД по дивидендам» попадало в `СД`;
- `Другое` — всё остальное.
- Статус `expected`, если в заголовке есть «ожидается» или «предварительно»; иначе `confirmed`.

**`toRawRows(events, source)`** — мост в БД:

```typescript
export interface CalendarRawRow {
  source: string
  date: string
  weekday: string
  title: string
  kind: EventKind
  status: EventStatus
  company: string
  ticker: string
}
```

Одно событие с N компаниями порождает N raw-строк. Тикеры приводятся к uppercase. Заголовок и `kind` дедуплицируются на этапе `rebuildCanonical`, но в raw-слое хранятся как есть.

**Верификация:**

```bash
npm run verify:calendarAdapters
```

Скрипт `scripts/calendar-m2-verify.js` проверяет:
1. `investmint` и `smartlab` корректно определяют свои форматы и отклоняют чужие.
2. `detectAdapter()` не путает семплы, отмечает ambiguous-файлы.
3. Парсинг investmint даёт ненулевое число событий, 0 `invalidDates`, и «СД по дивидендам» → `СД`.
4. Парсинг smartlab даёт ненулевое число `UNKNOWN`-тикеров.
5. `toRawRows()` возвращает корректный shape.
6. **Parity с фронтом:** backend-события по ключу `date|title|kind|status|tickers` совпадают с событиями, полученными из замороженных фронтовых парсеров (`tests/calendarAdapters/reference/frontend.js`).

## 6. Критические правила (наследуются из DESIGN_SPEC)

1. **Только реальные данные.** Никаких мок-событий при работающем бэкенде; источник упал → `stale: true` и честная плашка, не выдуманные даты
2. **server_date — единственный источник «сегодня».** Запрещено вычислять текущую дату на клиенте
3. Статус `expected` всегда визуально отличим от `confirmed` — нельзя выдавать прогнозную дату за подтверждённую
4. Тексты UI — через `src/lib/copy.ts` (single source of truth)
5. Все кликабельные элементы — `pointer-events-auto`
6. **Безопасность админских ошибок:** неожиданные 500 в CRUD событий (`/api/admin/calendar/events*`) отдают клиенту `{ error: "Internal error" }`; детали SQL-ошибки остаются только в серверных логах. Ошибки валидации (400/404/409) по-прежнему передают понятный текст.

## 8. Критерии приёмки

1. Блок виден на главной всем пользователям (гость — без подсветки портфеля)
2. Выбранный по умолчанию день = server_date (или ближайший событийный) — при любом часовом поясе устройства
3. Лента дат скроллится свайпом и драгом; выбранный день автоцентрируется
4. Группы >6 компаний сворачиваются/разворачиваются с анимацией
5. Статусы «ожидается/подтверждено» отображаются корректно и различимы
6. Тикеры из портфеля подсвечены в списке и на чипах дат
7. Skeleton → контент; ошибка → сообщение + «Повторить»; пустой день → empty state
8. После перехода через полночь (возврат во вкладку) календарь переключается на новое «сегодня» без перезагрузки страницы
9. `stale: true` → жёлтая плашка, данные всё равно показываются
10. Фильтры покрывают все 6 типов (МСФО/РСБУ/СД/СА/Дивиденды/Другое): фильтрация меняет список, счётчик и приглушение чипов дат; выбор сохраняется между визитами
11. Lighthouse: нет layout shift при загрузке блока (фикс. min-height на skeleton)
