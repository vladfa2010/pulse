# Инцидент 2026-10-08: недоступность логина, зависшие AIO-запросы и физическое повреждение таблицы `news`

**Статус:** закрыт (восстановление завершено 2026-10-08 ~18:20 МСК)
**Автор разбора:** backend-инженер (Kimi Code)
**Назначение документа:** развёрнутый postmortem для внешнего аудита. Содержит симптомы, методику расследования, исходные логи, принятые решения и рекомендации.

---

## 1. Резюме (TL;DR)

Пользователи не могли войти в приложение: запрос логина выполнялся ровно ~30 секунд и возвращался с ошибкой/пустым списком тегов, фронтенд показывал «Сервер не отвечает».

Расследование показало, что проблема имела **два независимых слоя**:

1. **Зависание асинхронного IO (AIO) в PostgreSQL 18.** IO worker'ы (io_uring) на ядре `7.0.0-34-generic` зависали и крутились на 100% CPU часами (это и была «загрузка CPU 200%» в панели хостера). Запросы, попадавшие на AIO, висли в ожидании `AioIoCompletion` до истечения `statement_timeout` (30 с) — отсюда характерное «ровно 30.1 секунды» у логина.

2. **Физическое повреждение данных на диске.** В heap-файле таблицы `news` обнаружен повреждённый регион из 17 страниц (блоки 1791–1807) с невалидными контрольными суммами. Ключевой диагностический факт: прямое чтение блока с диска (`O_DIRECT`) и чтение через page cache возвращали **разное содержимое** — симптом бага на уровне ядра/хранилища, а не PostgreSQL.

**Восстановление:** пересборка таблицы `VACUUM FULL` (таблица переписана в новый файл, битые страницы исключены), перестройка HNSW-индекса, отключение AIO-префетча, тюнинг памяти PostgreSQL. Потеряно ~120 старых новостей, физически расположенных на повреждённых страницах (восстановлению из кластера не подлежали; имелся свежий ночной бэкап).

**Итог:** логин 30.1 с → 0.3–0.6 с, ошибок контрольных сумм нет, мониторинг чистый.

## 5. Расследование: шаг за шагом

### 5.1. Локализация: это не фронт, не сеть и не «медленный запрос»

Замер снаружи (повторён 3 раза, разброс < 0.2 с):

```
$ curl -s -o /dev/null -w '%{http_code} %{time_total}s' -X POST \
    https://pulse.inside-trade.ru/api/auth/login \
    -H 'Content-Type: application/json' \
    -d '{"email":"vladfa@ya.ru","password":"!1234567890"}'
200 30.508964s
```

Ответ при этом содержал валидный JWT, но `tags: []`.

Код логина (`pulse-backend/src/routes/auth.ts:294`, ТЗ-05) синхронно вызывает `getUserTagsFull()` — теги пользователя включаются в ответ логина. В `pulse-backend/src/services/tagManager.ts:996` агрегат `news_per_month` считается подзапросом:

```sql
SELECT ntl.tag_id, COUNT(DISTINCT ntl.news_id)
FROM news_tag_links ntl
JOIN news n ON n.id = ntl.news_id
WHERE n.published_at > $2
  AND ntl.tag_id IN (SELECT tag_id FROM portfolios
                     WHERE user_id = $1 AND is_frozen = FALSE)
GROUP BY ntl.tag_id
```

EXPLAIN (без ANALYZE) показывал дешёвый план (~49k cost: parallel seq scan `news_tag_links` 41k строк + `news` 21k за месяц). То есть планировщик запрос **не считал** тяжёлым. Но EXPLAIN ANALYZE не завершался **более 10 минут**, процесс висел в `IO / AioIoCompletion`. Запрос был убит через `pg_terminate_backend`.

Вызов `getUserTagsFull` обёрнут в `try/catch → return []`: при ошибке/таймауте логин всё равно завершается, но без тегов и после 30-секундного ожидания. Это объясняло и 30.1 с, и пустой `tags`.

### 5.2. Зависшие AIO: «200% CPU» и мёртвые запросы

Снимок активности (16:57):

```
  pid  | state  | wait_event_type |   wait_event    |     dur      | query
-------+--------+-----------------+-----------------+--------------+-------
 259696| active | IO              | AioIoCompletion | 00:14:14.85  | SELECT count(*) FROM news;
 260274| active | IO              | AioIoCompletion | 00:03:57.23  | SELECT count(*) FROM news;
 260261| active | IPC             | ExecuteGather   | 00:03:57.23  | SELECT count(*) FROM news;
 260427| active | IO              | AioIoCompletion | 00:00:27.75  | WITH window_tags AS (... articles_30
 260440| active | IO              | AioIoCompletion | 00:00:24.77  | SELECT id, title_ru, summary_ru, url ...
 260459| active | IO              | AioIoCompletion | 00:00:24.61  | WITH ranked AS (... ROW_NUMBER() OVER ...
 260464| active | Lock            | relation        | 00:00:08.61  | ANALYZE news (matched_tags, published_at)
```

И процессы хоста:

```
USER    PID     %CPU  TIME      COMMAND
999     850003  97.8  259:12    postgres: io worker 1        ← spin ~4.3 часа CPU
```

Диагноз этого этапа: в PostgreSQL 18 асинхронный IO (io_uring внутри io worker'ов) **зависает и не завершается**. Сами запросы честно ждут завершения AIO и гаснут только по `statement_timeout`. Один io worker при этом бесконечно крутится в userspace — в панели хостера это выглядит как «CPU 200%».

Важная деталь: ручной `VACUUM (ANALYZE) news`, запущенный в 16:23, за **более чем 6 часов** просканировал лишь 1676 из 43383 heap-страниц (`pg_stat_progress_vacuum`, фаза `scanning heap`, `delay_time=0` — то есть не троттлинг vacuum'а, а реально зависшие чтения).

### 5.3. Перезапуск postgres → истинная картина диска

После `docker restart pulse-postgres` (17:16) IO перестал зависать (io worker'ы — 0.0% CPU), и первый же seq scan показал настоящую проблему данных:

```
Timing is on.
ERROR:  invalid page in block 1799 of relation "base/17577/17854"
CONTEXT:  parallel worker
Time: 67.044 ms
```

(файл `base/17577/17854` = heap таблицы `news`, проверено через `'news'::regclass::oid`.)

Чтение с `zero_damaged_pages=on` проходило, и сразу выяснилось ещё две вещи:

**а) Повреждён регион, а не одна страница.** Autovacuum-скан зафиксировал:

```
2026-10-08 17:19:02.445 UTC [34] LOG:  page verification failed, calculated checksum 6016 but expected 20376
... (для каждого блока 1792–1804 «calculated» разный, а «expected» ОДИН И ТОТ ЖЕ 20376)
2026-10-08 17:19:02.445 UTC [34] ERROR:  13 invalid pages among blocks 1789..1804 of relation "base/17577/17854"
2026-10-08 17:19:02.445 UTC [34] DETAIL:  Block 1792 held the first invalid page.
```

Одинаковое «expected 20376» на всех страницах региона — страницы заполнены паттерном чужих данных (см. вывод в §7).

**б) `zero_damaged_pages` не лечит диск.** Обнуление происходит только в памяти текущего бэкенда и **не помечает буфер dirty** — на диск ничего не пишется. Проверено экспериментально: обнуление → `CHECKPOINT` → прямое чтение файла — блок прежний:

```
WARNING:  invalid page in block 1799 of relation "base/17577/17854"; zeroing out page
 201933
CHECKPOINT
--- проверка файла на уровне ОС (O_DIRECT, обход page cache) ---
0000000 000510 000000 057760 113634 136533 000000 000100 002740   ← данные, не нули
```

### 5.4. Рассинхрон page cache и O_DIRECT — ключевой эксперимент

Одно и то же чтение блока 1799 двумя способами (подряд, секунды):

```
$ dd ... iflag=direct  (минуя page cache):  0000000 000510 000000 057760 113634 ...
$ dd ...              (через page cache):  0000000 000443 000000 010340 146410 ...
```

Содержимое **разное** при обоих способах отличном от нулей. Вывод: page cache хоста отдаёт устаревшую/иную копию, а на диске лежит другой битый образ. Это уже не PostgreSQL — это слой виртуализации/блочного устройства/ядра 7.0. Такое поведение согласуется с картиной §5.2: «зависшие» чтения io_uring — вероятно, чтения, которым ядро/гипервизор никогда не возвращали данные.

Дополнительно по региону: md5 всех 16 блоков 1789–1804 попарно различны; свип-скан PostgreSQL в тот момент ругался только на 1799 — то есть часть «битых» чтений была фантомами несвежего кэша, а физически повреждённым оказался итогово регион 1791–1807 (зафиксировано при VACUUM FULL, см. §6).

### 5.5. Свип всей БД

Детекция повреждений по всем пользовательским таблицам (обнуление в памяти, без записи):

```sql
SET zero_damaged_pages = on;
DO $$ DECLARE r RECORD; n BIGINT;
BEGIN
  FOR r IN SELECT schemaname, relname FROM pg_stat_user_tables
           WHERE schemaname='public'
  LOOP
    EXECUTE format('SELECT count(*) FROM %I.%I', r.schemaname, r.relname) INTO n;
  END LOOP;
END $$;
```

**Результат:** повреждения только в `news`. Остальные таблицы (включая `news_tag_links`, 28 МБ) — чистые. Это позволило не восстанавливать кластер целиком.

## 6. Восстановление

### 6.1. Снятие блокировщиков

Два тяжёлых аналитических запроса (`SELECT p.user_id, COUNT(DISTINCT ntl.news_id) ... FROM portf...`, панель «Аналитика») зависли в тех же AIO-спинах, держали `AccessShareLock` на `news` и не отзывались на `pg_terminate_backend` (SIGTERM не обрабатывается в spin-loop; оба крутились ~100% CPU, накопив 11 и 3.7 мин CPU). Оба сняты `kill -9` на хосте — с ожидаемым side-effect: аварийное завершение всех backend'ов и crash recovery (данные не пострадали, WAL цел).

### 6.2. VACUUM FULL

Первые попытки `VACUUM (FULL, ANALYZE) news` упирались в блокировщиков; после их снятия и остановки backend-контейнера (чтобы читатели не мешали ACCESS EXCLUSIVE) пересборка прошла. HNSW-индекс (`news_embedding_hnsw`) предварительно снесён — иначе pgvector перестраивает граф при FULL-пересборке, а при `maintenance_work_mem=32MB` это заняло бы часы:

```
NOTICE:  hnsw graph no longer fits into maintenance_work_mem after 6966 tuples
DETAIL:  Building will take significantly more time.
```

Итог пересборки:

```
WARNING:  zeroing out 15 invalid pages among blocks 1791..1806 of relation "base/17577/17854"
DETAIL:  Block 1792 held the first zeroed page.
HINT:  See server log for the other 14 zeroed block(s).
WARNING:  invalid page in block 1807 of relation "base/17577/17854"; zeroing out page
VACUUM
```

- `news`: **1391 МБ → 691 МБ** (heap 334 → 232 МБ; заодно убраны ~5800 dead tuples и раздутая статистика).
- Строк: 201 933 → **201 813** (−120: новости, физически лежавшие на 17 битых страницах; восстановлению из кластера не подлежат).
- `count(*)` без флага обнуления — чистый, ошибок чексумм нет.

### 6.3. Возврат в строй и перестройка HNSW

Backend запущен: логин **0.47 с**, 28 тегов с реальными `news_per_month`.

Постройка HNSW сначала упёрлась в дефолтный `/dev/shm` docker-контейнера (64 МБ):

```
ERROR:  could not resize shared memory segment "/PostgreSQL.3801594502"
        to 265326368 bytes: No space left on device
```

Исправлено `shm_size: 1gb` в compose. Индекс перестроен за ~10 минут с `maintenance_work_mem=256MB` (восстановленный размер ~510 МБ).

### 6.4. Конфигурационный тюнинг (зафиксирован в git)

| Параметр | Было | Стало | Почему |
|---|---|---|---|
| `shared_buffers` | 128 МБ | **384 МБ** | Таблица `news` (~700 МБ после чистки) не влезала в кэш — каждый запрос шёл на диск; хост имеет 3.9 ГБ RAM |
| лимит памяти контейнера | 320 МБ | **896 МБ** | Иначе shared_buffers упирался в cgroup (риск OOM-килла postgres) |
| `maintenance_work_mem` | 32 МБ | **128 МБ** | Постройка индексов при 32 МБ деградировала на порядки |
| `effective_cache_size` | 256 МБ | **1792 МБ** | Планировщик недооценивал кэш и выбирал неоптимальные планы |
| `effective_io_concurrency` | 16 | **0** | Отключение AIO-префетча (io_uring зависал) |
| `maintenance_io_concurrency` | 16 | **0** | То же для VACUUM/ANALYZE |
| `/dev/shm` контейнера | 64 МБ | **1 ГБ** | DSM-память параллельных построек индексов |

Коммиты: `f8346f0` (тюнинг + отключение AIO), `7854829` (`shm_size`). Значения продублированы в `command:` compose — он единственный источник правды; `postgresql.auto.conf` (ALTER SYSTEM) сохранён как дополнительный слой.

## 7. Причинно-следственный анализ

**Что подтверждено фактами:**

1. AIO (io_uring) на данном стеке `PG 18.6 + ядро 7.0.0-34` зависает: io worker в userspace-spin ~4.3 ч CPU; запросы в `AioIoCompletion` до statement_timeout; чтения «не возвращаются» ни через 10+ минут.
2. Данные на диске физически повреждены (контрольные суммы не сходятся) в непрерывном регионе 17 страниц; содержимое страниц — чужой повторяющийся паттерн (одинаковый «expected checksum 20376» на разных блоках), характерный для misdirected/перезаписанного сторонними данными региона.
3. Page cache расходится с содержимым диска (`O_DIRECT` ≠ buffered) — когерентность кэша на уровне ядра/гипервизора нарушена.
4. Итоговый дефект логина = совпадение двух факторов: запрос тегов попадал на зависший AIO-путь (30 с → пустые теги), а после перезапусков — на seq scan с битыми страницами.

**Гипотезы, которые не подтвердились и были отвергнуты:**

- «Планировщик выбрал плохой план» — EXPLAIN давал ~49k cost; отклонено.
- «Нехватка индексов на `news_tag_links`» — индексы `(tag_id)`, `(tag_id, news_id)` присутствуют; seq scan 41k строк при исправном IO — доли секунды; отклонено данными §5.2 (запросы висели в AioIoCompletion, а не в CPU/IO-ожидании выполнения).
- «Bloat/dead tuples делают скан медленным» — real count 201k строк, heap 334 МБ; при живом IO такой скан — <1 с (подтверждено после восстановления: `count(*)` = 0.5–0.7 с на холодном кэше, 83 мс на тёплом).
- «zero_damaged_pages лечит» — отвергнуто экспериментом §5.3-б: обнуление не сбрасывается на диск.

**Наиболее вероятная первопричина:** дефектный стек хранения/ядра у хостера (mainline-ядро 7.0 + io_uring + блочное устройство ВМ): одновременно объясняет и зависшие AIO-завершения, и рассинхрон page cache, и misdirected-записи. Вторичный фактор — недопараметризованный контейнер БД (320 МБ лимит / 128 МБ shared_buffers / 64 МБ shm), из-за чего любая деградация IO сразу становилась пользовательской.

## 9. Что не делалось (и почему)

- **pg_upgrade на PG 17 / смена образа** — отложено: восстановление VACUUM FULL дало рабочее состояние за минуты вместо часов простоя миграции. Рекомендуется отдельным планом (PG17 без AIO либо PG18 на исправленном ядре).
- **VACUUM FULL с живым HNSW** — осознанно прервано: граф не влезал в 32 МБ и перестраивался бы часами; индекс пересоздан отдельно.
- **Полный ребилд кластера из бэкапа** — не потребовался: повреждение локализовано в одну таблицу, свип остальных таблиц чистый.

## 10. Рекомендации

1. **Ядро — критично.** Откатить на стабильную ветку (6.8/6.11 HWE) или эскалировать хостеру с приложенными фактами: io worker spin 259 мин CPU, `AioIoCompletion`-вечные ожидания, рассинхрон `O_DIRECT`/page cache, misdirected-записи. Повторение повреждений данных на этом стеке — вопрос времени.
2. **Мониторинг:** алерты на (а) backend в состоянии `AioIoCompletion`/`DataFileRead` дольше N секунд, (б) CPU io worker'ов > 50%, (в) «invalid page» в логах postgres, (г) p95 логина.
3. **Регулярный `amcheck`** (`bt_index_check` по индексам `news`) + контроль `pg_stat_user_tables.n_dead_tup` на предмет метаболизма bloat'а.
4. **Проверить целостность бэкапов на восстановление** — pg_dump до инцидента мог молча ошибаться на битых страницах; сделать тестовый restore последнего nightly.
5. Периодический `ANALYZE news` (статистика `n_live_tup` отставала на порядки).
6. Рассмотреть переезд БД на выделенное накопительное устройство/другой тариф с гарантированным IO — текущий дисковый отклик (полный скан 340 МБ — десятки секунд при холодном кэше) — сам по себе узкое место.

## Приложение А. Ключевые команды восстановления

```bash
# 1. Диагностика зависших запросов
docker exec pulse-postgres psql -U pulse_user -d pulse -c \
  "SELECT pid, state, wait_event, now()-query_start, left(query,100)
   FROM pg_stat_activity WHERE state != 'idle' ORDER BY 4 DESC;"

# 2. Отключение AIO (до пересоздания контейнера)
ALTER SYSTEM SET effective_io_concurrency = 0;
ALTER SYSTEM SET maintenance_io_concurrency = 0;
SELECT pg_reload_conf();

# 3. Детекция повреждений (обнуление только в памяти, без записи!)
psql -c 'SET zero_damaged_pages = on;' -c 'SELECT count(*) FROM <table>;'

# 4. Проверка блока на уровне ОС (обход page cache)
docker exec pulse-postgres sh -c \
  'dd if=$PGDATA/base/17577/17854 bs=8192 skip=1799 count=1 iflag=direct | od -N 64 | head'

# 5. Пересборка таблицы
psql -c 'SET zero_damaged_pages = on;' -c 'VACUUM (FULL, ANALYZE) news;'

# 6. Перестройка HNSW
psql -c "SET maintenance_work_mem = '256MB';" \
     -c 'CREATE INDEX news_embedding_hnsw ON news USING hnsw (embedding vector_cosine_ops);'
```
